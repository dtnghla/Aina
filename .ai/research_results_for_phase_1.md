# 1. Labeling Point Cloud Data

**Extracting BIM Geometry:** Start by exporting the BIM geometry (pipes, walls) from Revit as 3D models and transformations. The user’s script already obtains transformation matrices and `.obj` files for each element in Revit. Using these, align the raw point cloud to the BIM model coordinate system. This alignment ensures points and BIM objects share a common frame. 

**Assigning Labels via Distance Threshold:** For each point in the cloud, find the nearest BIM element (from the exported `.obj`). If the point lies within a small distance (threshold) of a BIM surface, label it as that element’s class (e.g., pipe or wall). Points beyond the threshold remain unlabeled (they might be noise or objects not in the BIM). This nearest-neighbor search can be accelerated with a k-d tree due to the large number of points. For example, if a point is within, say, 2 cm of a wall mesh, assign it the “wall” label. This procedure effectively transfers BIM labels onto the point cloud. 

**Verification and Separate Storage:** After labeling, verify a subset of points to ensure the threshold was appropriate (too small might miss points, too large could cause mislabeling of nearby elements). In future iterations, plan to store the labels externally instead of modifying the LAZ files. For instance, maintain a parallel file (or extra point attributes) that contains the label and instance ID for each point. This way, the original LAZ (geometry + color) stays intact, and labels can be updated or refined without rewriting the entire point cloud. Many point cloud formats (like LAS/LAZ) support extra dimensions or classification fields that could hold labels, but an external label map (e.g., a CSV or a sidecar file) is simple and keeps the LAZ file read-only.

**Handling Unmodeled Points:** If some scan points don’t correspond to any BIM object (e.g., temporary objects or scan noise), they will remain unlabeled. These can either be assigned a special “unclassified” label or filtered out. In a later stage (change detection), such points could be clustered to flag unidentified objects, but for training the model, you may exclude them or mark them as background. Ensuring a clean labeled dataset (points labeled only as pipe, wall, or background) will make the model training more effective.

# 2. Training the PointGroup Model (Pointcept) with LAZ Data

**Environment Setup:** Begin by setting up the Pointcept codebase (which includes PointGroup). Install any additional dependencies and compile the custom operations. For PointGroup, an extra library is needed – install Google SparseHash (for efficient clustering) and compile the PointGroup ops. In the Pointcept repository, this involves running the provided commands: for example, `conda install -c bioconda google-sparsehash`, then building the ops by navigating to `libs/pointgroup_ops` and running the setup script. After compiling, enable PointGroup in the code by uncommenting the corresponding import line (e.g., `from .point_group import *`) in `pointcept/models/__init__.py`. This makes the PointGroup model accessible for training.

**Dataset Preparation with Laspy:** Prepare your labeled LAZ dataset in a format the model can consume. You can use **laspy** in Python to read LAZ files directly. For each LAZ file (each scan or each scene), use `laspy.read("file.laz")` to load it. This gives a `LasData` object from which you can extract point coordinates and attributes (e.g., `las.x, las.y, las.z` for coordinates). Ensure the coordinates are scaled properly (laspy provides scaled values via lowercase properties `las.x` vs the raw integers `las.X`). Also retrieve the labels for each point (which you stored separately during labeling). You may need to combine the geometry from the LAZ with the label array (e.g., using point indices). A common approach is to produce a training data file per scene containing columns for x, y, z, (maybe color), semantic label, and instance ID. For example, you can create a NumPy array or `.npy`/`.pth` file with shape [N, 6] (XYZRGB + labels) or similar structure that PointGroup expects.

**Integrating Custom Data into Pointcept:** Pointcept’s codebase has preprocessing scripts for datasets like ScanNet and S3DIS. Emulate those for your data. If your point clouds are large, consider chunking or voxel downsampling to manage memory. You might write a custom preprocessing script that reads each LAZ, attaches labels, and stores the data in the expected directory structure (e.g., `data/your_dataset/train/...` etc.). If Pointcept requires data in a specific format (like `.pth` files containing point arrays and annotations), convert your LAZ data accordingly. In many instance segmentation pipelines, each scene is stored as a dictionary or tuple (point coordinates, per-point semantic labels, per-point instance IDs). Follow the format used by ScanNet in Pointcept: their preprocess script likely outputs a `.pth` for each scene. You can do similarly: for each labeled LAZ, save a `.pth` containing something like: `{ coords: float[N,3], colors: uint8[N,3] (optional), semantic_labels: int[N], instance_labels: int[N] }`. Update or create a dataset class in `pointcept/datasets` for your custom dataset if needed, or reuse an existing one by mimicking its expected folder/file structure.

**Data Augmentation and Preprocessing:** Apply augmentations to increase model robustness. Common point cloud augmentations include random rotations (e.g. around the vertical axis for indoor scenes so the model is rotation-invariant to room orientation), jittering (adding small Gaussian noise to coordinates), scaling, and flipping. Also consider random subsampling or voxelization during training to reduce point count and introduce variation in point density. PointGroup (and Pointcept) may already implement some augmentations in the training config. Check the config file you will use (for example, `configs/your_dataset/insseg-pointgroup-*.py`) for augmentation settings such as rotation angles or jitter sigma. If needed, specify these in the config or the data loader. Preprocessing can also include normalizing coordinates (if the scale varies) or translating the scene so that the model doesn’t become sensitive to absolute coordinates. For indoor scans, you might want to center each room or use the coordinate system as-is if all scenes share a common reference.

**Configuring the Training Pipeline:** Pointcept uses configuration files to set model type, backbone, dataset path, classes, and training hyperparameters. Create a config for your dataset by copying an example (like the ScanNet config for PointGroup). Update the number of semantic classes (for instance, if you only care about “pipe” and “wall”, you might have those two plus one for “background/others” – ensure the config knows the class names and counts). Also set the dataset name and root directory in the config. PointGroup typically uses a backbone (like SpUNet or Minkowski U-Net) for feature extraction – you can use the default (as in the ScanNet PointGroup config) unless you have specific needs. 

**Training Execution:** Launch training using the Pointcept training script. The repository provides a convenient shell script interface. For example, you might run: 

```bash
sh scripts/train.sh -g 2 -d <your_dataset_name> -c <your_config_name> -n <experiment_name>
``` 

This will start training on 2 GPUs (`-g 2`) using your dataset and config. The script handles setting up `tools/train.py` with the given config. Alternatively, run the training directly with Python: 

```bash
export PYTHONPATH=./:$PYTHONPATH 
python tools/train.py --config-file configs/<your_dataset>/<config>.py --num-gpus 2
``` 

The training process will create an `exp/<your_dataset>/<experiment_name>` folder to save model checkpoints, logs, and backups of the config. Monitor the training via logged metrics or TensorBoard logs in that folder. Training time will depend on dataset size and model complexity – for example, training on a few million points with a PointNet/SpUNet backbone might take several hours to a couple of days on a modern GPU. 

**Validation during Training:** If you have a validation set of labeled point clouds, PointGroup can evaluate instance segmentation performance (like mAP or precision) after certain epochs. Ensure your dataset split (train/val/test) is defined. The config can specify evaluation intervals. This helps catch issues like the model overfitting or struggling with a particular class. 

# 3. Running Inference on New Point Clouds

**Loading the Trained Model:** Once training is complete, use the final or best checkpoint for inference. Pointcept provides a testing script to perform inference on point clouds. Use the corresponding test script or command for your experiment. For example: 

```bash
sh scripts/test.sh -g 1 -d <your_dataset_name> -n <experiment_name> -w model_best
``` 

This uses one GPU and loads the `model_best.pth` checkpoint by default. The test script will look for data in the dataset’s test split. To run inference on a new unlabeled LAZ file (not in the original dataset), you have a few options:
- **Option A:** Add the new point cloud into your dataset structure as a “test” scene (with a dummy label file). You can create an entry in the data list for this scene. Since it’s unlabeled, you won’t have ground truth to evaluate, but the script can still generate predictions.
- **Option B:** Write a small custom inference script using Pointcept’s model APIs. This involves loading the checkpoint weights into the model and directly feeding a point cloud. For example, use `laspy` to read the LAZ, obtain the points, and preprocess them the same way as training (apply scaling, voxelization or chunking if the model expects it). Then pass the points through the model to get semantic labels and offsets, and apply the PointGroup clustering algorithm (which is part of the model’s forward pass). Pointcept likely wraps all this in the test pipeline, so Option A (using the provided test script) may be simpler.

**Ensuring Data Format Consistency:** Before running inference, make sure the new point cloud is processed in the same way as training data. If during training you voxelized or scaled points, do the same for the input. In practice, the test script in Pointcept will handle splitting a large point cloud into chunks (if needed) and stitching results. This allows inference on a full-size scan without running out of memory, and yields more accurate results than naive downsampling. So if your new point cloud is large (millions of points), rely on the built-in test routine to tile it into grids for prediction.

**Obtaining the Output:** The model’s output for instance segmentation will typically be: for each point, a semantic class and an instance ID. PointGroup specifically produces clusters of points representing each detected object (each cluster has a predicted semantic label like “pipe” or “wall”). The test script should save the results in a structured format. For example, it may output a file per scene (perhaps in `exp/<dataset>/<experiment>/predictions/...`) that contains the predicted label for each point. If not, you can modify the test script to save results. A convenient output format is a labeled point cloud file – e.g., a LAS file with the **classification field** set to the semantic label (pipe=1, wall=2, etc.) and an extra field or separate list for instance IDs. Another approach is to output a JSON or CSV where each instance is recorded with its points or with summary geometry (centroid, dimensions – which we will compute in the next step).

**Integrating with Revit Workflow:** The end goal is to bring the detection results into Revit, which likely cannot handle millions of raw points directly. Instead of importing the segmented point cloud, you will **extract geometric primitives** from the clusters (next section) and use those. Thus, the inference output should be post-processed to a **usable format for geometry extraction**. For example, you can output the list of points (or their indices) for each detected instance. If using a custom script, you can directly call geometry fitting functions on each cluster of points and output the fitted parameters (like centerline and radius for a pipe). If using the test script, you might have it save a simple text file: each line could correspond to one instance, containing all point coordinates or some summary. Storing every point isn’t strictly necessary if you plan to immediately fit geometry – you could compute the geometry on the fly. 

In summary, run the model on new scans by mirroring the training data process (using the test script or a similar pipeline), then obtain per-point predictions. The result is effectively an **annotated point cloud** where each point knows which pipe or wall it belongs to. This is the input for the geometric analysis in the next step.

# 4. Extracting Geometric Information from Model Predictions

**Clustering Points into Instances:** With the model’s output, group the points by their instance ID. Each group ideally corresponds to a single physical element – e.g., all points with instance ID 5 might be one pipe. You already have these clusters from PointGroup (that’s the essence of the instance segmentation). Now, for each cluster, determine if it’s a pipe or a wall (use the semantic label). This lets you decide which geometric model to fit.

**Wall Geometry via Plane Fitting:** For clusters labeled as *wall*, the shape is typically planar and vertical. Use a plane fitting algorithm (such as RANSAC for robust fit) to find the plane that best fits the points. RANSAC will ignore outliers like a few stray points. The output is a plane equation (normal vector and distance from origin). From the plane, compute orientation and dimensions:
- The **normal vector** gives the wall’s orientation. In Revit, you’ll use this to determine the wall’s facing direction (the normal can indicate which side is interior/exterior if needed).
- To get the wall’s extents, project the wall’s points onto the fitted plane. Then, find the bounding box of these projected points. A simple way is to take the two principal directions in the plane (you can do a PCA on the point coordinates restricted to the plane). The largest spread will correspond to the wall’s length, and the smaller spread (if any) might correspond to wall thickness. However, if the point cloud is only one face of the wall, thickness cannot be directly measured. In that case, use a standard wall thickness or metadata from BIM if available.
- The **wall height** can be determined by taking the difference between the maximum and minimum Z values of the wall’s points (assuming Z is vertical). Typically, interior walls will have points from floor to ceiling. If the scan didn’t capture the full height (e.g., ceiling not scanned), you might use building floor height data. The transformation matrix from Revit could help – for instance, if you know the wall runs from Level 1 to Level 2 at a known height, you can use that. But if not, using the point cloud’s top and bottom is a start.

Each wall instance can thus be summarized by: a base line (defined by two end points along the floor or base of wall), a height, a thickness, and a normal direction. For example, you might compute that Instance #7 (wall) lies on a plane with normal (1,0,0) and spans from (x1,y1,z_floor) to (x2,y2,z_floor) at base, with height H. This information will be used to create a wall in Revit at the correct location and size.

**Pipe Geometry via Cylinder Fitting:** For clusters labeled as *pipe*, fit a cylinder model to the points. Use a RANSAC cylinder fitting approach (available in PCL, Open3D, or implement manually). The RANSAC algorithm will find the best cylinder that explains the cluster, yielding parameters: the cylinder’s central axis line (defined by a line through space), the radius, and potentially the length (if the ends of the cylinder are within the cluster). Key steps:
- Estimate normals for the point cluster (if using an algorithm that requires point normals, though some RANSAC implementations don’t need them).
- Run RANSAC with a cylinder model, adjusting parameters like distance threshold (how close points must be to the cylinder surface to count as inliers). You might set the distance threshold to a few centimeters to account for scan noise. Also, you can constrain the radius range if you know typical pipe diameters in your data (e.g., between 5 cm and 50 cm).
- The result will give you the cylinder’s axis direction and a point on the axis, plus the radius. From the cluster’s bounding points, you can infer the **endpoints** of the pipe along that axis (e.g., project all points onto the axis line, then take min and max projections to get the ends of the pipe segment that was scanned).

Each pipe instance is summarized by: a start point, an end point, and a diameter. For example, Instance #3 (pipe) might be fitted with a cylinder of radius 0.1 m whose axis runs from (X1, Y1, Z1) to (X2, Y2, Z2). If the pipe appears straight (which it should for a single segment), this axis is effectively the pipe’s centerline in 3D.

**Quality Checks:** After fitting, it’s wise to validate the geometry:
- Did the plane normal for a wall make sense (e.g., roughly horizontal plane normals for walls should be near vertical axis for floor/ceiling or near horizontal for walls)? If your pipeline might also detect floors/ceilings, ensure you don’t confuse them. In this project, we focus on walls (vertical planes) and pipes (cylinders).
- Did the cylinder fitting find a reasonable radius? If the cluster was small or sparse, RANSAC might fail or find a trivial “cylinder”. If that happens, you might use a simpler approximation: connect the furthest apart points in the cluster to define the axis and measure radius by average distance from that axis. But typically, RANSAC should succeed if the cluster is indeed cylindrical.

**Using BIM Metadata (Optional):** If the initial BIM model (from which labels came) is available and you assume the as-built geometry hasn’t changed much, you could cross-check your fitted dimensions with the BIM element. For example, if a pipe cluster was labeled using a BIM pipe of diameter 0.2 m, you could directly use that diameter instead of measuring from points (which might reduce noise). Similarly, wall thickness could be fetched from the BIM model. However, if the point of this system is to work on new scans where BIM data isn’t present, then rely on the point cloud measurements alone.

After this step, for each detected instance of pipe or wall, you will have **geometric parameters**: location (line or plane position), orientation, and size (length/height, radius/thickness). This forms the basis for creating corresponding elements in Revit.

# 5. Revit 2022 Add-in for Reconstruction

**Development Setup:** To integrate with Revit 2022, create an add-in using C# (since Revit API is best supported in .NET languages). Use Visual Studio to create a Class Library project targeting *.NET Framework 4.8* (Revit 2022 uses .NET 4.8 ([System Requirements for Revit 2022 - Microsol Resources](https://microsolresources.com/tech-resources/article/system-requirements-for-revit-2022/?srsltid=AfmBOorT3Z-0m4rxDNFo7uhXwFwJfJCTllJ4uwYEdLhPxJd1EyQJd5ff#:~:text=,registration%20and%20prerequisite%20component%20download))). Reference the Revit API assemblies (RevitAPI.dll and RevitAPIUI.dll) in your project – these are found in Revit’s install directory. Implement the `IExternalCommand` interface for your add-in command, which requires a public `Execute` method ([
	The Revit API: Creating Your First Add-In | DMC, Inc.

](https://www.dmcinfo.com/latest-thinking/blog/id/9326/the-revit-api-creating-your-first-add-in#:~:text=,in%20Revit%20API)). Mark your class with `[Transaction(TransactionMode.Manual)]` or similar so you can control the database changes in Revit ([
	The Revit API: Creating Your First Add-In | DMC, Inc.

](https://www.dmcinfo.com/latest-thinking/blog/id/9326/the-revit-api-creating-your-first-add-in#:~:text=should%20do%20before%20actually%20writing,It%27s%20usually%20a)). 

**Add-in Manifest:** Create an `.addin` XML file (in `%AppData%/Autodesk/Revit/Addins/2022`) to register your plugin with Revit ([
	The Revit API: Creating Your First Add-In | DMC, Inc.

](https://www.dmcinfo.com/latest-thinking/blog/id/9326/the-revit-api-creating-your-first-add-in#:~:text=1.%20Write%20an%20add,we%27ve%20already%20done%20this%20one)). This file will specify the full path to your compiled DLL, the name of your command, and other details. When Revit starts, it will read this manifest and load your add-in, making the command available in the UI (usually under the *Add-Ins* tab -> External Commands).

**Reading the Geometry Data:** Your add-in needs to get the pipe and wall parameters extracted in step 4. If you saved the results to a file (JSON, CSV, etc.), the add-in can read that file when executed. Alternatively, you could embed the process of steps 3 and 4 into the add-in (for instance, have the add-in itself load the point cloud and do inference by calling an external Python script or using an ML.NET model if converted). However, keeping inference separate and just feeding final geometry to Revit is simpler and avoids heavy computation inside Revit. Assuming a file-based approach: choose a format like CSV where each line is an element with type, coordinates, etc., or a JSON with a list of elements. The add-in’s `Execute` can prompt the user to select the file or use a fixed path.

**Creating Wall Elements:** Loop through each detected wall entry. For each wall, you have (from step 4) a base line (two points) and a height (and maybe a thickness and normal). Revit’s API provides a static method to create walls by line:
```csharp
Line baseLine = Line.CreateBound(pointStart, pointEnd);
WallType wallType = new FilteredElementCollector(doc).OfClass(typeof(WallType))
                      .Cast<WallType>().FirstOrDefault(wt => wt.Name.Contains("Basic"));
Level level = /* get a Level object, e.g., the base level for this wall */;
Wall wall = Wall.Create(doc, baseLine, wallType.Id, level.Id, height, 0, false, false);
``` 
This uses `Wall.Create(document, curve, wallTypeId, levelId, height, offset, flip, structural)` to make a wall. In this call, `height` is the wall height (distance from base level), and `offset` is set to 0 if the wall starts at the level. You can set `flip` to true/false depending on which side of the line you want the wall’s exterior (the normal direction from step 4 can guide this – if the normal points outward, you might not need to flip). Set `structural` to false unless these are structural walls. 

Before calling these creation methods, make sure you start a **Transaction** in the Revit API, as all changes must occur within a transaction. For example:
```csharp
using(Transaction t = new Transaction(doc, "Create Walls and Pipes"))
{
    t.Start();
    // ... create walls and pipes ...
    t.Commit();
}
``` 
This ensures all elements are created as one atomic operation (or you can separate transactions per element type). 

**Creating Pipe Elements:** For each pipe entry, use the Revit MEP API. You’ll need a PipeType and a MEP system type. Revit requires pipes to belong to a system (e.g., Hydronic Supply, Domestic Water, etc.). You can retrieve an arbitrary system type ElementId via filtered search (or if you know the system, use that). For example:
```csharp
MEPSystemType systemType = new FilteredElementCollector(doc).OfClass(typeof(MEPSystemType))
                            .Cast<MEPSystemType>().FirstOrDefault();
PipeType pipeType = new FilteredElementCollector(doc).OfClass(typeof(PipeType))
                      .Cast<PipeType>().FirstOrDefault();
Level level = /* appropriate level for the pipe, maybe the lower of its endpoints */;
XYZ start = new XYZ(x1, y1, z1);
XYZ end   = new XYZ(x2, y2, z2);
Pipe pipe = Pipe.Create(doc, systemType.Id, pipeType.Id, level.Id, start, end);
``` 
This uses the `Pipe.Create` method which takes the document, system type, pipe type, level, and the start/end points of the centerline. The radius/diameter of the pipe is inherent in the PipeType (i.e., the family type defines diameter). If your detected pipes have varying diameters, you might need multiple PipeTypes – one for each diameter. In Revit, PipeTypes are usually loaded for standard sizes. You can either pick the closest size or create a new type programmatically for the exact diameter. For simplicity, if the differences are small, pick an existing type. If accuracy is needed, you can duplicate an existing PipeType and set its diameter parameter.

After creating the pipe, you might also need to assign its **connectors or routing** if it should attach to existing geometry. But if these are standalone detections, just creating straight pipe segments is sufficient. Revit will place them according to the start and end XYZ. Ensure that XYZ coordinates you use are in Revit’s internal units (feet by default). If your point cloud was in meters, you must convert (1 meter = 3.28084 feet). Neglecting unit conversion is a common mistake – the pipes/walls will be created, but at the wrong scale in the Revit scene.

**Best Practices for Revit Integration:** 
- **Transaction Management:** Group element creation in transactions. It’s fine to create many elements in one transaction, but be mindful of performance if the number is huge (hundreds of elements can still be okay).
- **Element Types:** Use appropriate element types. For walls, ensure the WallType chosen is correct (e.g., an architectural wall type). For pipes, ensure the family is a piping family, otherwise `Pipe.Create` will throw exceptions if the types or system are invalid.
- **Levels and Constraints:** Place walls and pipes on the correct levels. If a wall spans multiple levels, you might create it on the base level with the full height. If a pipe spans vertically across levels, you might still create it on the base level; Revit can represent it as one continuous pipe as long as it’s one element. Alternatively, split by level if needed. 
- **Revit 2022 Compatibility:** Since you target Revit 2022, use .NET 4.8 as mentioned and the Revit 2022 API DLLs ([System Requirements for Revit 2022 - Microsol Resources](https://microsolresources.com/tech-resources/article/system-requirements-for-revit-2022/?srsltid=AfmBOorT3Z-0m4rxDNFo7uhXwFwJfJCTllJ4uwYEdLhPxJd1EyQJd5ff#:~:text=,registration%20and%20prerequisite%20component%20download)). The API calls shown (Wall.Create, Pipe.Create) are available in 2022. There were no breaking changes from 2021 to 2022 for these basic functions. Just ensure your add-in manifest is for 2022 (the <RevitVersion> in the .addin can be 2022 or a range including it).


**Potential Challenges and Risks:**
- *Label Noise:* The automatic labeling using BIM models might introduce errors. For instance, misalignment between the point cloud and BIM model could cause points to be assigned to the wrong wall, especially with a generous distance threshold. This could confuse the model during training. Mitigation: manually inspect and clean the labeled point clouds, or implement a sanity check (e.g., ensure that a point labeled as wall actually has neighboring points similarly labeled – if not, it might be an outlier).
- *Class Imbalance:* You might have far more wall points than pipe points (walls are large surfaces, pipes are smaller). The model could bias toward the wall class. Mitigation: use data augmentation or sampling strategies so the model sees a balanced set, or adjust loss weighting to emphasize pipe accuracy.
- *Model Performance:* PointGroup is a fairly advanced model and might require a good GPU and sufficient memory. If the point clouds are huge, training on full scenes might be slow or impossible; chunking or subsampling might be needed. Also, instance segmentation quality can vary – the model might merge two close pipes or split one wall into segments if not well tuned. Expect some iteration in training (adjusting hyperparameters, or even trying a different model/backbone if needed). It’s important to set aside time for experiments and not assume the first training run yields perfect results.
- *Inference Generalization:* If the model is trained on data from one building and you apply it to a completely different building’s scan, differences in scanner noise or element shapes could affect results. The plan assumes the training data is representative of the target environment (same sensor type, similar construction).
- *Geometry Extraction Edge Cases:* Not all clusters will fit the ideal shapes perfectly. For example, if a wall has a doorway that wasn’t modeled, the cluster could be two planes (above and below the door) – the plane fitting might still work, but the bounding box will include the doorway gap as if filled with wall points (since they’re missing). This might result in a wall that covers the door. Similarly, pipes with bends might be segmented into separate straight pieces by the model, but if not, a curved or elbow-shaped cluster would break the cylinder model. To manage this, you could impose assumptions (e.g., only fit straight segments – which is reasonable for many pipe networks) and possibly post-process: if a pipe cluster seems very long and changes direction, split it and fit two cylinders.
- *Revit Integration:* Creating geometry in Revit may reveal coordinate mismatches. A common risk is unit conversion errors (point cloud often in meters, Revit in feet). Another is level assignment – if everything is placed on level 0 with tall heights, in Revit that might span multiple storeys without clean floor separation. You might need to programmatically decide which Revit level to use (for example, if a wall’s base Z is 3.2m, that’s likely “Level 1” in a building where Level 1 is at 0 and floor-to-floor height ~3m; you may then assign it to Level 1 and height up to Level 2).
- *Testing and Iteration:* After the first end-to-end integration, plan for a testing period. Take a point cloud, run it through the entire pipeline, and load the results in Revit. Verify that the created walls and pipes align with the original point cloud (you can overlay the point cloud in Revit to check). There will likely be adjustments – e.g., you might find the need to offset a wall’s baseline to floor level exactly, or that pipes are slightly off-center. Fine-tuning the extraction calculations or the add-in’s placement logic will be necessary. Allocate time for this debugging (perhaps 1 extra week).
